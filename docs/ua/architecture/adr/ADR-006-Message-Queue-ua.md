# ADR-006: Вибір черги повідомлень

**Статус**: Прийнято зі змінами: події Spring із реєстром публікацій подій Spring Modulith (доповнення 2026-10-09); Kafka лише для споживача поза застосунком  
**Дата**: 2025-08-20  
**Автор**: Стефан Костик  
**Зацікавлені сторони**: Архітектор проекту, Команда розробки, Команда операційного відділу

---

## Контекст

Система моніторингу та відстеження нагород потребує черги повідомлень для архітектури на основі подій, асинхронної обробки та роз'єднання системних компонентів. Це підтримує журнали аудиту, сповіщення та майбутню міграцію до мікросервісів.

### Передумови
- Архітектура на основі подій для подій життєвого циклу нагород
- Асинхронна обробка для парсингу документів та сповіщень
- Вимоги журналу аудиту GDPR через event sourcing
- Потреби комунікації майбутніх мікросервісів

---

## Рішення

> Змінено доповненням 2026-10-09: усередині застосунку події є подіями Spring, які записує реєстр публікацій
> подій Spring Modulith. Kafka, як описано нижче, лишається варіантом для споживача поза застосунком.

**Apache Kafka** було обрано як рішення черги повідомлень для Системи моніторингу та відстеження нагород.

### Обраний підхід
- **Message Broker**: Apache Kafka 3.0+
- **Інтеграція**: Spring Kafka з автоконфігурацією Spring Boot
- **Топіки**: Топіки специфічні для подій (award-events, user-events, document-events)
- **Розгортання**: Один broker для розробки, кластер для продакшену

### Обґрунтування
- **Event Sourcing**: Ідеально підходить для ведення журналів аудиту та історії подій
- **Масштабованість**: Горизонтальне масштабування та можливості високої пропускної здатності
- **Довговічність**: Персистентне зберігання подій з налаштовуваним періодом зберігання
- **Інтеграція Spring**: Відмінна інтеграція Spring Kafka
- **Корпоративне прийняття**: Промисловий стандарт для систем на основі подій

## Наслідки

### Позитивні наслідки
- **Роз'єднання**: Слабке зв'язування між системними компонентами
- **Журнал аудиту**: Повна історія подій для відповідності GDPR
- **Масштабованість**: Асинхронна обробка покращує чутливість системи

- **Складність**: Додатковий компонент інфраструктури для управління
- **Крива навчання**: Концепції та найкращі практики Kafka
- **Використання ресурсів**: Вимоги до пам'яті та диска для зберігання повідомлень

## Розглянуті альтернативи

### Альтернатива 1: RabbitMQ
- **Переваги**: Простіше налаштування, добре для шаблонів запит-відповідь, UI управління
- **Недоліки**: Нижча пропускна здатність, менше підходить для event sourcing
- **Причина відхилення**: Kafka краще підходить для архітектури на основі подій

### Альтернатива 2: Amazon SQS
- **Переваги**: Керований сервіс, відсутність накладних витрат на інфраструктуру
- **Недоліки**: Прив'язка до постачальника, вищі витрати, обмежені функції event sourcing
- **Причина відхилення**: Перевага open-source рішення для портфоліо

## Примітки з реалізації

### Технічні вимоги
- **Версія Kafka**: 3.0+ для останніх функцій та продуктивності
- **Інтеграція Spring**: Spring Kafka 3.0+
- **Сховище**: Мінімум 10GB для зберігання подій
- **Пам'ять**: 2GB heap для Kafka broker

### Схема подій
```json
{
  "eventType": "award.created",
  "eventId": "uuid",
  "timestamp": "2025-01-16T10:30:00Z",
  "source": "award-service",
  "subject": "award-123",
  "data": { /* корисне навантаження події */ }
}
```

### Конфігурація топіків
- **award-events**: Події життєвого циклу нагород (створено, затверджено, опубліковано)
- **user-events**: Події управління користувачами (зареєстровано, оновлено)
- **document-events**: Події обробки документів (завантажено, проаналізовано)

## Доповнення 2026-10: Реалізацію відкладено

В епіках 1 і 2 брокер повідомлень не розгорнуто. Записи аудиту та знімки версій нагород пишуться синхронно,
у тій самій транзакції, що й зміна, яку вони описують, тож історія ніколи не розходиться з даними. Листи, що
супроводжують зміну (підтвердження адреси, зміни ролей і делегувань, новий пристрій, експорт даних),
надсилаються після фіксації транзакції через внутрішньопроцесні події Spring (пакети `event`); сповіщень у
застосунку ще немає.

Вибір між Apache Kafka та внутрішньопроцесними подіями Spring робиться на старті епіку 7 (сповіщення), коли
з'явиться перший асинхронний споживач. Рішення вище лишається еталонним варіантом.

## Доповнення 2026-10-05: Події Spring із реєстром публікацій

Напрям після огляду архітектури 2026-10-04, підтверджений на старті епіку 7 (див. доповнення 2026-10-09):

- Усередині застосунку події залишаються внутрішньопроцесними подіями Spring. Реєстр публікацій подій
  Spring Modulith зберігає кожну подію в PostgreSQL у транзакції, що її публікує, і позначає її завершеною після
  успішної обробки, тож збій процесу чи невдалий лист більше не губить подію, а незавершені публікації
  повторюються під час запуску. Брокер для цього не потрібен.
- Kafka з'являється лише тоді, коли події потрібні споживачу поза застосунком (інша система, сервіс, виділений
  за критеріями ADR-022). Тоді Spring Modulith може передавати вибрані події в Kafka без зміни видавців.
- Рядки аудиту й версії нагород залишаються синхронними, у транзакції зміни.

До кінця епіку 4 листи після коміту працювали без реєстру; збій між комітом і надсиланням втрачав цей лист.
Історія 7.1.1 запровадила реєстр (доповнення 2026-10-09).

## Доповнення 2026-10-09: Рішення, реєстр публікацій подій

**Рішення.** Події всередині застосунку є подіями Spring. Кожен `@TransactionalEventListener`, що виконується
після коміту, записує реєстр публікацій подій Spring Modulith (`spring-modulith-starter-jdbc` 1.4, таблиця
`event_publication`, міграція V036): один рядок на слухача пишеться в транзакції, що публікує подію, і
видаляється, коли слухач завершується без помилки (`spring.modulith.events.completion-mode: delete`). Відкат не
лишає рядка й не запускає слухача.

**Доставка щонайменше один раз.** `MailDelivery` робить три спроби надіслати лист, а тоді кидає
`MailNotDeliveredException`, тож публікація лишається незавершеною. Завдання `PublicationRetry` запускається кожні
10 хвилин (перший запуск через 1 хвилину після старту) і повторно подає незавершені публікації, старші за 10 хвилин
і молодші за 24 години; після перезапуску нічого додатково робити не треба, бо перший запуск підхоплює те, що
лишив попередній процес. Старші публікації більше не повторюються, про них щоразу пишеться один рядок помилки;
через 30 днів їх видаляють із попередженням у журналі. Збій після надсилання, але до видалення рядка, надсилає
лист удруге; такий дублікат прийнятний. Налаштування: `app.events.retry-interval`, `retry-after`, `give-up-after`,
`keep-failed`, `first-run`. Метрики `award.events.incomplete` і `award.events.abandoned` у `/actuator/prometheus`.

**Тимчасові події.** Події з одноразовим посиланням (`VerificationRequested`, `PasswordResetRequested`,
`EmailChangeRequested`, `EmailChanged`, `NewDeviceSignedIn`) ніколи не зберігаються: посилання в базі було б
дійсним обліковим даним. Їх публікує `AfterCommit` після коміту, а обробляють звичайні `@EventListener`; невдале
надсилання записується в журнал, і користувач запитує нове посилання. `AccountLocked` публікується поза
транзакцією й лишається звичайним слухачем. `ObjectStored` зберігає свого слухача після відкату, якого реєстр не
записує.

**Правила для нових подій.** Подія реєстру має перетворюватися на JSON і назад за допомогою `ObjectMapper`
застосунку (один тест на тип) і не може містити секретів. Імена класу й методу слухача є ключем реєстру:
перейменування чи переміщення слухача з незавершеними рядками робить їх сиротами, тож така зміна виходить, коли
таблиця порожня.

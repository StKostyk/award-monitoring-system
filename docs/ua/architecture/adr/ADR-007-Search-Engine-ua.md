# ADR-007: Вибір пошукової системи

**Статус**: Прийнято (на практиці замінено повнотекстовим пошуком PostgreSQL, див. доповнення 2026-10-26)  
**Дата**: 2025-08-20  
**Автор**: Стефан Костик  
**Зацікавлені сторони**: Архітектор проекту, Команда розробки

---

## Контекст

Система моніторингу та відстеження нагород потребує розширених можливостей пошуку для нагород, документів та профілів користувачів. Це включає повнотекстовий пошук, фасетний пошук та аналітику для функцій звітності.

### Передумови
- Повнотекстовий пошук по описах нагород та документах
- Фасетний пошук для фільтрації нагород за критеріями
- Аналітика пошуку для відстеження використання та інсайтів
- Підтримка багатомовного контенту (англійська/українська)

---

## Рішення

**Elasticsearch 8+** було обрано як пошукову систему для Системи моніторингу та відстеження нагород.

### Обраний підхід
- **Пошукова система**: Elasticsearch 8+ (остання стабільна версія)
- **Інтеграція**: Spring Data Elasticsearch з Spring Boot
- **Розгортання**: Один вузол для розробки, кластер для продакшену
- **Випадки використання**: Пошук нагород, пошук контенту документів, аналітика

### Обґрунтування
- **Повнотекстовий пошук**: Розширені можливості аналізу тексту та оцінювання
- **Продуктивність**: Швидкий час відповіді пошуку з оптимізацією індексування
- **Багатомовність**: Відмінна підтримка декількох мов та аналізаторів
- **Аналітика**: Вбудовані агрегації для аналітики пошуку та звітності
- **Інтеграція Spring**: Хороша підтримка Spring Data Elasticsearch

---

## Наслідки

### Позитивні наслідки
- **Продуктивність пошуку**: Час відповіді пошуку менше секунди
- **Користувацький досвід**: Розширені функції пошуку покращують зручність використання
- **Аналітика**: Багата аналітика пошуку для інсайтів та звітності
- **Масштабованість**: Горизонтальне масштабування для великих обсягів документів

### Негативні наслідки
- **Використання ресурсів**: Значні вимоги до пам'яті та CPU
- **Складність**: Додатковий компонент інфраструктури для управління
- **Крива навчання**: Elasticsearch query DSL та оптимізація

## Розглянуті альтернативи

### Альтернатива 1: Apache Solr
- **Переваги**: Сильне управління конфігурацією, хороша документація
- **Недоліки**: Складніше налаштування, менше cloud-native функцій
- **Причина відхилення**: Elasticsearch краща хмарна інтеграція

### Альтернатива 2: PostgreSQL повнотекстовий пошук
- **Переваги**: Відсутність додаткової інфраструктури, просте налаштування
- **Недоліки**: Обмежені функції пошуку, погана масштабованість для складних запитів
- **Причина відхилення**: Недостатньо для розширених вимог пошуку

## Примітки з реалізації

### Технічні вимоги
- **Версія Elasticsearch**: 8.0+ для останніх функцій безпеки та продуктивності
- **Інтеграція Spring**: Spring Data Elasticsearch 5.0+
- **Пам'ять**: Мінімум 4GB heap для продакшену

## Доповнення 2026-10: Реалізацію відкладено

В епіках 1 і 2 застосунок не використовує Elasticsearch. Списки нагород, фільтри та перевірка дублікатів
працюють на PostgreSQL (специфікації JPA; подібність `pg_trgm` для можливих дублікатів); підказка категорії
зіставляє масиви `award_categories.keywords`.

Elasticsearch присутній лише в необов'язковому стеку моніторингу (`infra/docker-compose.monitoring.yml`) як
сховище журналів (див. доповнення до ADR-011). Повнотекстовий пошук нагород вирішується на старті епіку 5.

## Доповнення 2026-10-05: Спершу оцінюється повнотекстовий пошук PostgreSQL

На старті епіку 5 повнотекстовий пошук PostgreSQL оцінюється раніше за Elasticsearch: `tsvector` за українською
та англійською назвами, організацією, що нагороджує, і описом з індексом GIN у поєднанні з наявною схожістю
`pg_trgm` для друкарських помилок. Один університет має щонайбільше десятки тисяч нагород, які PostgreSQL
шукає за мілісекунди, а дані залишаються в одному сховищі з тими самими правилами доступу та резервними копіями.
Elasticsearch обирається, лише якщо оцінювання покаже потребу, якої PostgreSQL не задовольняє (налаштування
релевантності для кількох мов, фасети на великих обсягах, пошук між університетами).

## Доповнення 2026-10-26: Повнотекстовий пошук PostgreSQL є пошуковою системою

Функція 5.4 реалізує пошук на PostgreSQL (міграція V047). Два згенеровані збережені стовпці таблиці `awards`
містять тексти для пошуку: `search_vector` (конфігурація `simple`; назви з вагою A, організація-нагороджувач B,
описи C; апострофи вилучено) і `search_text` (назви та організація-нагороджувач у нижньому регістрі), кожен з
індексом GIN (`idx_awards_search`, `trgm_awards_search`). PostgreSQL 17 не має українського стемера, тому на боці
запиту з кожного слова відтинаються до двох кінцевих голосних, а кожна основа зіставляється як префікс
(`прем:* & шевченк:*`). У списках досягнень зіставляється також ім'я власника. Триграмна схожість слів не менше
0,5 за назвами та організацією-нагороджувачем є резервним пошуком для одруківок і виконується лише тоді, коли жодна
нагорода не відповідає словам.

Виміряно на 100 000 затверджених нагород (масштабний тест історії 5.4.1, PostgreSQL 17): ранжований пошук за двома
словами з 1 666 збігами триває близько 200 мс у базі даних і відповідає через API швидше ніж за 1 с в обох списках;
пошук з одруківкою через триграмний індекс триває 16 мс. Триграмне зіставлення, об'єднане через OR із
повнотекстовим, тривало 1,7 с для поширених слів (перевірка 10 000 рядків-кандидатів), тому воно стало резервним.
Elasticsearch не застосовується, доки не виникне одна з умов доповнення 2026-10-05.

Історія 5.4.2 (міграція V048) перенесла правила розбору слів в одну функцію `search_words()` (IMMUTABLE), яку
викликають обидві згенеровані колонки: нормалізація NFC, апострофи вилучаються, кожна послідовність інших символів
читається як пробіл. Тому злитий токен, як-от `2024-2025`, `3.5` чи `chnu.edu.ua`, стає окремими словами і в
збереженому тексті, і в запиті; літери, введені в розкладеному вигляді, знаходяться, а ім'я власника знаходиться з
будь-яким апострофом чи пропусками. Функція міститься у V048, а не в повторюваній міграції, бо від неї залежать
згенеровані колонки; база розгортання має зберігати класифікацію символів `en_US.utf8`, на яку функція спирається.

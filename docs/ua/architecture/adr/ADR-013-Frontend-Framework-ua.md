# ADR-013: Вибір Frontend Framework

**Статус**: Прийнято  
**Дата**: 2025-08-21  
**Автор**: Стефан Костик  
**Зацікавлені сторони**: Архітектор проекту, Frontend команда, UX команда

---

## Контекст

Система моніторингу та відстеження нагород потребує сучасного, корпоративного frontend framework, здатного обробляти складні користувацькі інтерфейси, інтернаціоналізацію та інтеграцію з backend API. Framework повинен підтримувати TypeScript-first розробку та забезпечувати комплексний інструментарій для середовища одного розробника.

### Передумови
- Потреба в комплексному frontend framework з корпоративними функціями
- Вимога до TypeScript-first підходу розробки
- Складні вимоги UI, включаючи форми, таблиці даних та дашборди
- Підтримка інтернаціоналізації для англійської та української мов
- Інтеграція з Spring Boot backend API

### Припущення
- Контекст одного розробника вимагає відмінний інструментарій та документацію
- Корпоративне прийняття та підтримка спільноти критичні для довгострокової життєздатності
- Експертиза TypeScript цінна для демонстрації портфоліо
- Фреймворк повинен підтримувати як традиційні, так і прогресивні веб-додатки

## Рішення

**Angular 20+** було обрано як frontend framework для Системи моніторингу та відстеження нагород.

### Обраний підхід
- **Framework**: Angular 20+ (остання стабільна версія)
- **Мова**: TypeScript як основна мова розробки
- **Архітектура**: Компонентно-орієнтована архітектура з сервісами та модулями
- **Інструмент збірки**: Angular CLI для скаффолдингу проекту та управління збіркою

### Обґрунтування
- **Корпоративне прийняття**: Широко прийнятий в корпоративних середовищах з сильною підтримкою Google
- **TypeScript-First**: Нативна підтримка TypeScript з відмінним інструментарієм та типобезпекою
- **Комплексний фреймворк**: Підхід "батарейки включені"(з англ. повністю готовий) з роутингом, HTTP клієнтом, формами та тестуванням
- **Підтримка спільноти**: Велика спільнота, обширна документація та сторонні бібліотеки
- **Довгострокова підтримка**: LTS версії забезпечують стабільність для корпоративних додатків

## Наслідки

### Позитивні наслідки
- **Продуктивність розробника**: Комплексний CLI інструментарій та підтримка IDE
- **Типобезпека**: TypeScript забезпечує перевірку помилок під час компіляції та кращий рефакторинг
- **Корпоративні функції**: Вбудована ін'єкція залежностей, роутинг та HTTP інтерсептори
- **Підтримка тестування**: Комплексний тестувальний фреймворк з Karma та Jasmine
- **Документація**: Відмінна офіційна документація та навчальні ресурси

### Негативні наслідки
- **Крива навчання**: Крутіша крива навчання порівняно з React для розробників нових до Angular
- **Розмір бандлу(пакета)**: Більший початковий розмір пакета порівняно з легковаговими альтернативами
- **Фреймворк Lock-in**: Сильні переконання та конвенції можуть обмежувати гнучкість

### Нейтральні наслідки
- **Цикл релізів**: Регулярні основні релізи версій вимагають періодичних оновлень
- **Екосистема**: Велика екосистема з перевагами та складністю

## Розглянуті альтернативи

### Альтернатива 1: React
- **Переваги**: Велика екосистема, гнучкий, легковаговий, сильний ринок праці
- **Недоліки**: Потребує додаткових бібліотек для повного рішення, менш категоричний
- **Причина відхилення**: Комплексний підхід Angular краще підходить для корпоративних вимог

### Альтернатива 2: Vue.js
- **Переваги**: М'яка крива навчання, хороша продуктивність, гнучка архітектура
- **Недоліки**: Менше корпоративного прийняття, менш комплексний інструментарій
- **Причина відхилення**: Нижче корпоративне прийняття та TypeScript інтеграція

## Доповнення 2026-09: Режим рендерингу

Застосунок рендериться лише на боці клієнта. Серверний рендеринг (SSR) був у початковому каркасі, але його
прибрано до початку розробки функцій:

- Кожен екран доступний лише після автентифікації, тож SSR не дає переваг для SEO чи першого відображення
  анонімним відвідувачам.
- SSR потребує середовища Node у контейнері та коду, безпечного для гідратації, навколо API, доступних лише в
  браузері (зберігання токенів, PKCE), що ускладнює систему без користі для користувача.
- Статичну збірку віддає nginx (див. `frontend/Dockerfile`), що відповідає ADR-017.

Локалізація надається під час виконання за допомогою Transloco (`@jsverse/transloco`): одна збірка обслуговує
обидві мови, українська — за замовчуванням, англійська вмикається з панелі інструментів, а вибір
запам'ятовується в браузері. Підхід `$localize` під час компіляції розглянуто й відхилено: він створює окрему
збірку для кожної мови, подвоює маршрути та адреси перенаправлення, які має знати сервер авторизації, і
перетворює перемикання мови на повне перезавантаження.

Автентифікація в браузері використовує `angular-oauth2-oidc` як публічного клієнта OpenID Connect власного
сервера авторизації застосунку (потік коду авторизації з PKCE); токени зберігаються в session storage й
оновлюються автоматично.

## Доповнення 2026-10: Service worker і робота без з'єднання

Продуктова збірка — вебзастосунок, який можна встановити (функція 8.1, US-013). Робота без з'єднання —
запасний режим для форми нагороди, а не клієнт, що працює передусім офлайн:

- **`@angular/service-worker` замість Workbox.** Постачається з Angular, для кожної збірки пише хешований
  маніфест (`ngsw.json`) і має API `SwUpdate`; додатковий крок збірки не потрібен. Реєструється лише в продуктовій
  збірці (`registerWhenStable:30000`); `npm start` і збірка для e2e працюють без нього.
- **Політика кешу** (`frontend/ngsw-config.json`). Групи ресурсів містять лише оболонку: `index.html`, бандли,
  `favicon.ico`, переклади й шрифти. Єдина група даних `brand` (`/brand/**`, freshness, тайм-аут 3 с, 7 днів)
  зберігає файл бренду, маніфест і значки, які розгортання замінює без перезбирання і які не містять персональних
  даних. Відповіді API не кешуються.
- **Навігація на шляхи бекенда минає worker.** `navigationUrls` виключають `/api/`, `/oauth2/`, `/connect/`,
  `/.well-known/`, `/login`, `/logout`, `/error`, `/login-assets/`, `/swagger-ui/`, `/v3/api-docs`,
  `/privacy/<версія>/` і `/health`, тож сторінка входу й потік авторизації ніколи не отримують кешовану оболонку.
  Модульний тест читає конфігурацію й падає на кешованому шляху бекенда або пропущеному виключенні.
- **З'єднання.** `ConnectivityService` поєднує події браузера `online`/`offline` з результатами запитів до
  бекенда (статус 0 позначає сервер недосяжним, успішна відповідь — знову досяжним; запити до бекенда мають заголовок
  `ngsw-bypass`, поки сторінкою керує worker, бо інакше він сам відповідав би 504 на відсутню відповідь); компоненти читають його сигнал
  `online`. Без з'єднання запуск зберігає наявну сесію (документ discovery і профіль завантажуються, щойно сервер
  відповість, невдале оновлення токена повторюється один раз), відвідувач без сесії бачить сторінку «Немає
  з'єднання» замість переходу на вхід, а вихід видаляє токени лише на пристрої.
- **Оновлення.** `UpdatePromptService` перевіряє нову версію під час запуску, коли вкладка стає видимою, і кожні
  6 годин та пропонує її у snackbar; коли перезавантажити, вирішує користувач. Невідновний стан worker
  перезавантажує сторінку.
- **Файли worker** (`ngsw-worker.js`, `ngsw.json`, `safety-worker.js`) віддаються з `Cache-Control: no-cache`,
  маніфест — як `application/manifest+json`; політика безпеки вмісту не змінюється (`script-src 'self'` покриває
  worker з того самого походження).
- **Аварійне вимкнення.** Якщо віддавати `safety-worker.js` як `ngsw-worker.js` або видалити `ngsw.json`, worker
  під час наступної перевірки сам себе скасовує; застосунок далі працює без нього.

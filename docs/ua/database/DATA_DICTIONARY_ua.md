## 1. Домен Користувачів

### 1.1 Сутність: `users`

**Опис**: Центральна сутність ідентичності що представляє всіх користувачів системи включаючи співробітників, адміністраторів та затверджувачів. Містить облікові дані автентифікації та інформацію профілю.

**Бізнес-Правила**:
- Адреса електронної пошти повинна бути унікальною серед усіх користувачів
- Користувачі належать рівно одній первинній організації
- Переходи статусу: PENDING → ACTIVE ↔ INACTIVE → SUSPENDED → RETIRED/MEMORIAL
- Хеш пароля використовує алгоритм BCrypt з силою 12

### 1.2 Сутність: `user_roles`

**Опис**: Призначення ролей що пов'язують користувачів з конкретними ролями в організаційних контекстах. Підтримує часову дійсність для переходів ролей та відстеження історії.

**Бізнес-Правила**:
- Користувачі можуть мати кілька ролей у різних організаціях
- Період дійсності ролі не може мати `valid_to` раніше за `valid_from - 1`: відкликання завершує призначення попереднім днем, тож роль, забрана в день початку, завершується за день до старту, і цей день лишається вільним для нового призначення (V017)
- Поточні ролі - ті де `valid_from <= CURRENT_DATE AND (valid_to IS NULL OR valid_to >= CURRENT_DATE)`
- Одна й та сама роль у підрозділі може бути безстроковою лише один раз (`uk_user_roles_current`); нічого не видаляється, тож історія лишається доступною
- Ієрархія ролей визначає повноваження затвердження; роль надає лише той, хто має роль строго вищу за неї в тому самому піддереві підрозділів

| **Колонка** | **Тип Даних** | **Nullable** | **За Замовч.** | **Обмеження** | **Опис** |
|-------------|---------------|--------------|----------------|---------------|----------|
| `user_role_id` | `BIGSERIAL` | НІ | Авто | PK | Унікальний ідентифікатор призначення ролі |
| `user_id` | `BIGINT` | НІ | - | FK→users | Користувач що отримує роль |
| `role_type` | `VARCHAR(30)` | НІ | - | CK | Тип ролі (див. enum нижче) |
| `organization_id` | `BIGINT` | НІ | - | FK→organizations | Організаційний обсяг ролі |
| `valid_from` | `DATE` | НІ | `CURRENT_DATE` | - | Дата початку дії ролі |
| `valid_to` | `DATE` | ТАК | - | CK | Дата закінчення дії ролі (NULL=безстрокова); відкликання встановлює вчорашню дату |
| `created_at` | `TIMESTAMPTZ` | НІ | `CURRENT_TIMESTAMP` | - | Мітка часу створення запису |
| `created_by` | `BIGINT` | ТАК | - | FK→users | Адмін що призначив роль |

**Типи Ролей** (`role_type`):
| Значення | Опис | Рівень Дозволів |
|----------|------|-----------------|
| `EMPLOYEE` | Стандартний працівник | Подання власних нагород |
| `FACULTY_SECRETARY` | Секретар факультету | Затвердження першого рівня, звіти факультету |
| `DEAN` | Декан факультету | Затвердження другого рівня, управління факультетом |
| `RECTOR_SECRETARY` | Секретар ректора | Затвердження третього рівня, звіти університету |
| `RECTOR` | Ректор університету | Остаточні повноваження затвердження |
| `SYSTEM_ADMIN` | Технічний адміністратор | Конфігурація системи, управління користувачами |
| `GDPR_OFFICER` | Офіцер захисту даних | Відповідність приватності, експорт даних |

**Індекси**:
- `pk_user_roles` - Первинний ключ на `user_role_id`
- `idx_user_roles_user` - B-tree на `user_id`
- `idx_user_roles_org` - B-tree на `organization_id`
- `idx_user_roles_current` - Частковий індекс для активних ролей

### 1.4 Сутність: `one_time_tokens`

**Опис**: Одноразові токени, що надсилаються листом для підтвердження адреси, скидання пароля, відкликання з міркувань безпеки та зміни адреси для входу. Зберігається лише хеш SHA-256 токена; саме значення існує тільки в посиланні з листа.

**Бізнес-Правила**:
- Токен можна використати один раз: `used_at` встановлюється при першому використанні, наступні спроби відхиляються
- Строк дії за призначенням: `EMAIL_VERIFICATION` 24 години, `PASSWORD_RESET` 1 година, `SECURITY_REVOKE` 24 години, `EMAIL_CHANGE` 1 година
- Токен `EMAIL_CHANGE` містить запитану адресу в `new_email_address`; токен `SECURITY_REVOKE` після зміни адреси може містити попередню адресу для входу (V026), і його використання повертає обліковий запис на неї, якщо її не використовує інший обліковий запис; токени інших призначень адреси не містять. Підтверджена зміна прив'язує невикористані посилання користувача «це був не я» до старої адреси й видає ще одне для повідомлення на стару адресу; скидання пароля та посилання нового пристрою скасовують лише неприв'язані. Новий запит скасовує попередні невикористані токени `EMAIL_CHANGE` користувача; підтверджена зміна скасовує невикористані токени `PASSWORD_RESET`
- Прострочені й використані рядки видаляє заплановане очищення

| **Колонка** | **Тип Даних** | **Nullable** | **За Замовч.** | **Обмеження** | **Опис** |
|-------------|---------------|--------------|----------------|---------------|----------|
| `id` | `BIGSERIAL` | НІ | Авто | PK | Унікальний ідентифікатор токена |
| `token_hash` | `VARCHAR(64)` | НІ | - | UK | Шістнадцятковий дайджест SHA-256 токена |
| `user_id` | `BIGINT` | НІ | - | FK→users | Власник токена |
| `purpose` | `VARCHAR(30)` | НІ | - | CK | `EMAIL_VERIFICATION`, `PASSWORD_RESET`, `SECURITY_REVOKE`, `EMAIL_CHANGE` |
| `new_email_address` | `VARCHAR(255)` | ТАК | - | CK | `EMAIL_CHANGE`: запитана адреса для входу в нижньому регістрі, завжди присутня; `SECURITY_REVOKE`: адреса, яку слід відновити після зміни адреси, інакше null; null для інших призначень (GDPR: Персональні Дані) |
| `expires_at` | `TIMESTAMPTZ` | НІ | - | - | Момент, після якого токен відхиляється |
| `used_at` | `TIMESTAMPTZ` | ТАК | - | - | Момент використання (NULL, доки не використано) |
| `created_at` | `TIMESTAMPTZ` | НІ | `CURRENT_TIMESTAMP` | - | Мітка часу створення запису |

**Індекси**: `pk_one_time_tokens`, `uk_one_time_tokens_hash`, `idx_one_time_tokens_user`, `idx_one_time_tokens_expires`

**Зв'язки**: НАЛЕЖИТЬ ДО `users` (N:1) через `user_id`, видаляється разом із користувачем

### 1.5 Сутність: `user_devices`

**Опис**: Браузери, з яких користувач входив. Вхід із невідомим для користувача відбитком створює рядок і запускає лист-сповіщення.

**Бізнес-Правила**:
- Відбиток — дайджест SHA-256 родини браузера, родини операційної системи та accept-language
- Один рядок на користувача й відбиток; `last_used_at` і `last_ip_address` оновлюються при кожному вході
- Підтвердження «це був не я» (токен `SECURITY_REVOKE`) видаляє всі рядки користувача, тож після скидання пароля кожен браузер знову себе оголошує; рядки також видаляються разом із користувачем

### 1.6 Таблиці сервера авторизації

`oauth2_registered_client`, `oauth2_authorization` та `oauth2_authorization_consent` відповідають еталонній схемі Spring Authorization Server з рекомендованими нею змінами для PostgreSQL (`blob` → `TEXT`, `timestamp` → `TIMESTAMPTZ`). Їхні колонки належать бібліотеці й тут не перелічуються; `oauth2_authorization.principal_name` містить email користувача й індексується для запитів відкликання. Значення токенів в `oauth2_authorization` зберігаються як видані (GDPR: Конфіденційно); доступ до таблиці має лише роль застосунку.

### 1.7 Сутність: `role_delegations`

**Опис**: Тимчасова передача ролі затвердження колезі. Делегат позичає дозволи читання й затвердження ролі на обмежений період; управління користувачами ніколи не передається разом із делегуванням (V018).

**Бізнес-Правила**:
- Позичати можна лише чотири ролі затвердження: `FACULTY_SECRETARY`, `DEAN`, `RECTOR_SECRETARY`, `RECTOR` (`ck_role_delegations_type`)
- Делегант має мати цю роль у цьому підрозділі в день передачі й мати її сам: позичені повноваження далі не передаються
- Делегат має бути іншим активним користувачем із чинною роллю в піддереві підрозділу (`ck_role_delegations_parties`)
- Період обов'язковий з обох кінців і триває щонайбільше 90 днів (`ck_role_delegations_dates`); після `valid_to` він просто перестає діяти, без жодного фонового завдання
- Одночасно — одне чинне делегування ролі на підрозділ від одного делеганта: застосунок відхиляє періоди, що перетинаються
- Відкликане делегування зберігає свій рядок із `revoked_at` і `revoked_by`; відкликання основної ролі забирає позичене нею в тій самій транзакції, а переведення делегата на іншу кафедру забирає позичене для підрозділів, у яких він більше не має жодної ролі
- Кожен шлях відкликання блокує рядки, які завершує (`SELECT … FOR UPDATE`), тож два одночасні відкликання завершують делегування один раз
- Делегат має позичені повноваження в claim токена `delegations` (`ROLE:orgId:delegatorId`) і в `role_scopes`, а після відкликання його виводять з усіх пристроїв

## 2. Домен Нагород

### 2.1 Сутність: `awards`

**Опис**: Основна бізнес-сутність що представляє професійні досягнення, визнання та нагороди отримані працівниками. Містить як публічну інформацію про нагороду так і метадані.

**Бізнес-Правила**:
- Кожна нагорода належить рівно одному користувачу (власнику). Особиста нагорода (`recipient_org_id` NULL) отримана її власником; нагорода підрозділу (`recipient_org_id` встановлено, V027) отримана факультетом чи кафедрою, а її власником є секретар факультету чи декан, що внесли й подали її (власна чи делегована роль, область якої охоплює підрозділ)
- Нагорода підрозділу належить підрозділу: `organization_id` = `recipient_org_id` з першого збереження (`ck_awards_recipient`), тож читання в межах області та маршрутизація рецензентів слідують підрозділу; перевірка дублікатів порівнює її з нагородами того самого підрозділу лише (чернетки інших осіб залишаються поза увагою), і вона входить до експорту GDPR власника
- Нагорода вводиться як `DRAFT` і може бути збережена лише з назвою (українською чи англійською, `ck_awards_title`); категорія, організація, що нагороджує, і дата нагороди обов'язкові, щойно вона виходить зі стану `DRAFT` (`ck_awards_complete`, V020)
- `organization_id` особистої нагороди — кафедра власника: встановлюється при створенні чернетки, оновлюється при поданні й далі зберігається, тож читання в межах області та маршрутизація рецензентів не залежать від пізнішого переведення
- Змінювати чи видаляти `DRAFT` може лише власник; подану нагороду змінює лише робочий процес
- Нагороди повинні бути категоризовані через `category_id` до подання
- Статус нагороди слідує визначеній прогресії робочого процесу
- Перевірені нагороди відображають бейдж верифікації
- Бал впливу розраховується на основі рівня категорії та організації що нагороджує
- Нагороди публічно видимі (основна функція системи для прозорості)

- `ck_awards_title` - `title IS NOT NULL OR title_uk IS NOT NULL`

- `ck_awards_date` - перестворено як `award_date <= (now() AT TIME ZONE 'Europe/Kyiv')::date`; версія V005 порівнювала з датою сесії (UTC) і відхиляла нагороди з сьогоднішньою датою між 00:00 і 03:00 за київським часом
- `fk_awards_organizations` - `organization_id` → `organizations(org_id)`

**Подання** (`POST /awards/{id}/submit`): під блокуванням рядка чернетки `status` стає `PENDING`, `impact_score` — базовим балом рівня, `organization_id` — поточною кафедрою власника, створюється один рядок `award_requests` (`SUBMITTED`, `FACULTY_SECRETARY`) і в `audit_logs` записується рядок `AWARD_SUBMITTED` (`entity_type = 'awards'`, `entity_id` = нагорода). Чернетка, для якої в того самого власника є інша нагорода з тією самою `award_date` і подібністю `pg_trgm` щонайменше 0.6 за `title` або `title_uk` у нижньому регістрі, подається лише після підтвердження власником; тоді рядок аудиту містить `duplicateAcknowledged: true`. Повернута чи відкликана чернетка зберігає свій рядок `award_requests`: подання блокує його раніше за чернетку й використовує повторно (`SUBMITTED` на рівні, що повернув, після повернення; на початковому рівні після відкликання; рецензента знято, нові `submitted_at` і `deadline`), тож її `review_decisions` лишаються на хронології; рядок аудиту містить `resubmittedFrom`. Таку чернетку видалити не можна (409 `award-has-request`).

**Відкликання** (`POST /awards/{id}/withdraw`, V030): власник нагороди `PENDING`, чия заявка `SUBMITTED` чи `ESCALATED` без `current_reviewer_id`, переводить заявку в `WITHDRAWN` (термін null), а нагороду в `DRAFT` під тим самим блокуванням рядка заявки, що й узяття в роботу; до `audit_logs` пишеться `AWARD_WITHDRAWN` з попереднім статусом і рівнем.

- `idx_awards_user_status` - B-tree на `(user_id, status)`
- `idx_awards_category_date` - B-tree на `(category_id, award_date DESC)`
- `idx_awards_category_status` - B-tree на `(category_id, status)` (V012)
- `idx_awards_pending` - Частковий B-tree на `(user_id, created_at DESC)` де `status = 'PENDING'`

### 2.3 Сутність: `documents`

**Опис**: Метадані документів, прикріплених до нагород (функція 3.1). Вміст зберігається в приватному S3-бакеті `award-documents` (MinIO, ADR-021) і шифрується сховищем; у базі даних — лише метадані. Стовпці для результатів AI-парсингу зарезервовано для відкладених функцій OCR (3.2, 3.3).

**Бізнес-Правила**:
- Документи належать нагороді; `request_id` зарезервовано для документів, доданих під час повторного подання (епік 4)
- Завантаження та видалення лише в `DRAFT` власника; документи поданої нагороди незмінні (функція 3.1 D-5)

### 2.4 Сутність: `award_versions`

**Опис**: Один рядок на кожен збережений стан нагороди (функція 2.2, V023), який застосунок пише в транзакції зміни. **Бізнес-Правила**:
- Версія записується після збереження нагороди при створенні чернетки (`CREATED`), збереженні, що змінило `awards.version` (`UPDATED`; збереження без змін версії не пише), і поданні (`SUBMITTED`); невдале збереження версії не пише, бо відкочується разом зі зміною

- Власник читає всі версії, а читачі, чия область охоплює `awards.organization_id`, — починаючи з першої версії `SUBMITTED` (або `BASELINE` нагороди, поданої до V023)

## 3. Домен Робочого Процесу

### 3.1 Сутність: `award_requests`

**Опис**: Сутність відстеження робочого процесу для процесу затвердження нагород. Кожна нагорода має рівно один запит що відстежує її шлях через багаторівневий робочий процес затвердження.

**Бізнес-Правила**:
- Зв'язок один-до-одного з нагородами (кожна нагорода має рівно один запит)
- Рівні робочого процесу: Секретар Факультету → Декан → Секретар Ректора → Ректор
- Переходи відповідають таблиці ADR-023: рецензент затверджує, відхиляє, повертає чи передає вище на рівні запиту; затвердження нижче мінімального рівня категорії або передача вище (будь-який рівень нижче ректора) переводить запит на наступний не пропущений рівень із новим дедлайном і без рецензента; повернення віддає нагороду як чернетку без рецензента й дедлайну; затвердження й відхилення встановлюють `completed_at` (4.1.2)
- `deadline` — кінець періоду розгляду на поточному рівні: встановлюється при поданні як `submitted_at`, зсунутий на робочі дні рівня (з понеділка по п'ятницю, той самий київський час доби, тож перехід на інший час його не зсуває; початок у вихідні рахується з понеділка 00:00), і переставляється при кожній зміні рівня та повторному поданні робочим процесом епіку 4. Рівні факультету використовують `organizations.review_working_days` факультету, якщо його встановлено (4.2.1), рівні ректора та факультет без власного значення — `app.workflow.review-working-days` (за замовчуванням 3); зміна терміну не змінює вже збережених строків; для запитів, поданих до V024, заповнено як `submitted_at` + 3 дні, а строки, збережені до 2.1.8 (SCRUM-43), зберігають значення в календарних днях
- Очікуване завершення обчислюється під час читання й ніколи не зберігається: строк плюс період розгляду кожного рівня, що ще попереду на шляху затвердження (від секретаря факультету до вищого з мінімального рівня затвердження категорії та поточного рівня); рівень із простроченим строком отримує новий період від поточного моменту
- Прострочений запит позначається як прострочений із поясненням; він ніколи не передається вище й не закривається автоматично (`EXPIRED` лишається в обмеженні, не використовується)

### 3.2 Сутність: `review_decisions`

**Опис**: Індивідуальні рішення затвердження/відхилення прийняті на кожному рівні робочого процесу. Надає повний аудиторський слід процесу затвердження.

**Бізнес-Правила**:
- Кожне рішення прив'язане до одного запиту та одного рецензента
- Типи рішень: APPROVED, REJECTED, ESCALATED, RETURNED
- Рішення є незмінними після запису
- Коментарі обов'язкові для відхилень та повернень
- Мітка часу записує точний момент рішення

## 4. Домен Відповідності

### 4.1 Сутність: `audit_logs`

**Опис**: Комплексний аудиторський слід для всіх значних дій системи. Потрібен для відповідності GDPR та моніторингу безпеки.

**Бізнес-Правила**:
- Всі модифікації даних логуються автоматично через тригери
- Рядки тригерів містять автентифікованого виконавця в `user_id` і `correlation_id` запиту: менеджер транзакцій встановлює `app.current_user_id` і `app.correlation_id` через `set_config(…, true)` на початку транзакції запису запиту з токеном доступу (функція 2.2, D-3); зміни без автентифікованого виконавця (міграції, початкові дані, фонові завдання, вхід і реєстрація) залишають `user_id` порожнім, як і рядки, записані до 2.2.1
- Рядки тригерів беруть `entity_id` з власного ключа зміненого запису для `INSERT`, `UPDATE` і, починаючи з V023, `DELETE` (V013 брала `user_id` видаленого рядка, тож старіші рядки `DELETE` для `awards` вказують на власника, а для `user_roles` — на користувача)
- Журнали є незмінними (UPDATE/DELETE не дозволено)
- Період зберігання: 7 років (згідно вимог GDPR)
- Партиціонування за місяць для продуктивності
- Зберігає як старі так і нові значення для відстеження змін

**Типи Дій** (поширені значення):
- `INSERT`, `UPDATE`, `DELETE` - зміни рядків, записані тригерами аудиту (`entity_type` = назва таблиці); починаючи з V022 знімки рядків `users` не містять `password_hash` (раніші рядки його зберігають)
- `PROFILE_UPDATED`, `EMAIL_CHANGE_REQUESTED`, `EMAIL_CHANGED` - зміни власного облікового запису, записані застосунком (`entity_type` = `USER`, `entity_id` = користувач); зміна імені зберігає старі й нові значення лише змінених полів в `old_values`/`new_values` з їхніми назвами в `changed_fields`; події адреси містять запитану адресу або стару й нову адресу

- `PASSWORD_CHANGE` - Безпека
- `CONSENT_GRANTED`, `CONSENT_WITHDRAWN` - Приватність
- `DATA_EXPORT` - особа завантажила власні дані (`entity_type` = `GDPR`, `entity_id` = користувач; `new_values` містить кількість записів у кожному розділі-списку файлу)
- `AUDIT_EXPORT` - власник `audit:read` завантажив журнал аудиту нагороди у CSV (`entity_type` = `awards`, `entity_id` = нагорода, `user_id` = аудитор; `new_values` = записані `rows` і `truncated`, якщо старіші рядки понад 10 000 пропущено)
- `DOCUMENT_DOWNLOAD` - читач нагороди завантажив документ (`entity_type` = `documents`, `entity_id` = документ, `user_id` = читач; `new_values` = `awardId`); завантаження на сервер і видалення — це рядки тригера `INSERT` і `DELETE` з тим, хто викликав, як виконавцем (функція 3.1)
- `DOCUMENT_REJECTED` - антивірусний сканер відхилив завантаження (`entity_type` = `documents`, `entity_id` null, бо нічого не збережено, `user_id` = той, хто завантажує; `new_values` = `awardId` і знайдена ClamAV `signature`; ніколи не назва файлу) (функція 3.1.3)
- `REVIEW_BATCH` - рецензент застосував одне рішення до кількох нагород через `POST /reviews/decisions` (`entity_type` = `awards`, `entity_id` null, `user_id` = рецензент; `new_values` = `decision`, `items`, `done`, `failed`); кожна вирішена нагорода має також власний рядок `REVIEW_DECISION` (4.1.4)
- `REVIEW_PERIOD_CHANGED` - декан (власна роль або доручення) чи системний адміністратор змінив термін розгляду факультету через `PUT /organizations/{id}/review-period` (`entity_type` = `organizations`, `entity_id` = факультет, `user_id` = виконавець; `old_values`/`new_values` = `workingDays` (власне значення, null для типового) і `effectiveWorkingDays`; `new_values.delegatorId` за дорученням); незмінене значення рядка не пише (4.2.1)
- `DATA_DELETE` - Права GDPR
- `APPROVAL`, `REJECTION` - Рішення робочого процесу

**Індекси**:
- `pk_audit_logs` - Первинний ключ на `(log_id, created_at)` (партиціонований)
- `idx_audit_logs_user` - B-tree на `user_id`

## Додаток C: Представлення та Функції Нагород

Визначені в повторюваних міграціях `R__create_views.sql` і `R__create_functions.sql`; застосунок їх поки що не викликає (звіти — в епіку 5, затвердження — в епіку 4). Вони дотримуються тих самих правил, що й застосунок:

| Об'єкт | Правило |
|--------|---------|
| `vw_active_awards`, `vw_pending_requests` | Колонки підрозділу беруться з `awards.organization_id`, кафедри на момент подання, а не з поточної кафедри власника |
| `vw_award_statistics` | Нагорода враховується для `awards.organization_id` незалежно від поточної кафедри чи статусу облікового запису власника |
| `fn_calculate_impact_score(category_id)` | Базовий бал рівня категорії, що дорівнює `RecognitionLevel` (SPECIALITY 10, DEPARTMENT 20, COLLEGE 30, FACULTY 40, UNIVERSITY 50, LOCAL 60, REGIONAL 70, NATIONAL 80, INTERNATIONAL 100) |
